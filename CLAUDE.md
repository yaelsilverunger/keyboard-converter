# Keyboard Layout Converter - Project Context

## What this project is
A Windows desktop app (Electron) that converts text typed with the wrong keyboard language.
Example: typed `nv t,` with English keyboard while Hebrew was intended → converts to `מה את`.

## How to run
```bash
npm install   # first time only
npm start
```

## How to build a distributable .exe installer
```bash
npm install
npm run build
# output: dist/Keyboard Converter Setup 1.0.0.exe
```

## Project structure
```
keyboard-converter/
├── main.js          # Electron main process: tray, global hotkeys, clipboard logic
├── converter.js     # Keyboard layout mapping (Hebrew <-> English), used by both main and renderer
├── renderer.js      # Renderer process: drives the UI text boxes
├── index.html       # App window UI
├── styles.css       # Dark theme styling
├── scripts/
│   └── create-icon.js  # Generates icon.png (256x256 PNG) before electron-builder runs
├── package.json     # electron + electron-builder, build config
└── .gitignore
```

## Keyboard mapping used
Standard Israeli Hebrew keyboard layout. Each entry:
  Hebrew character produced → English character from the same physical key.
Defined in `converter.js` as `HEBREW_TO_ENGLISH`. The reverse (`ENGLISH_TO_HEBREW`) is derived automatically.

## How the app works
- Runs in the **system tray** (purple icon). Closing the window hides it; Quit is in the tray menu.
- **Ctrl+Shift+Z**: User selects wrong text → Ctrl+C → presses hotkey → app converts clipboard → simulates Ctrl+V to paste back.
- **Ctrl+Shift+X**: Converts clipboard content only. User pastes manually with Ctrl+V. Shows a notification with `"input" → "output"`.
- Auto-detects direction: Hebrew characters present → Hebrew→English, otherwise English→Hebrew.

## Known issues / quirks to be aware of

### clipboard.readText() returns a Promise
In the installed Electron version, `clipboard.readText()` behaves asynchronously.
**Fix already applied**: `readClipboardText()` in `main.js` uses `await Promise.resolve(clipboard.readText())`.
Do NOT revert this to a synchronous call - it will break and convert `[object Promise]` instead of the actual text.

### Ctrl+Shift+Z paste simulation
Uses VBScript (`cscript.exe`) to simulate Ctrl+V via `WScript.Shell.SendKeys`.
The VBS file is written to the OS temp directory at app startup (`initVbs()`).
This may not work in elevated/admin windows - Ctrl+Shift+X is the reliable fallback.

### Tray icon
Generated programmatically as a 16x16 PNG buffer using Node's built-in `zlib` (no external dependencies).
The build icon (`icon.png`, 256x256) is generated by `scripts/create-icon.js` at build time.

## What still needs work / possible improvements
- The Ctrl+V paste simulation (VBScript) is unreliable in some apps - a native solution (e.g. robotjs or @nut-tree/nut-js) would be more robust but requires native compilation.
- Only Hebrew <-> English is supported. Russian, Arabic etc. could be added to converter.js.
- No way to customize the hotkeys without editing the code.
- App does not auto-start with Windows - could be added via app.setLoginItemSettings().

## macOS support
- Hotkeys are Ctrl+Shift+Z / Ctrl+Shift+X on all platforms (Cmd+Shift+Z is Redo on Mac, so it is avoided).
- On Mac, Ctrl+Shift+Z copies the selection itself (simulated Cmd+C), converts, and pastes back - no manual Cmd+C needed. It waits 300ms first so the held Ctrl+Shift don't merge with the simulated keys.
- Key simulation on Mac uses `osascript` with `key code` (not `keystroke "v"`), because `keystroke` fails while the Hebrew layout is active.
- Paste simulation on Mac uses `osascript` (System Events). Grant Accessibility permission to Terminal/Electron/the app in System Settings > Privacy & Security > Accessibility.
- Build a Mac app: `npm run build:mac` (output in dist/).
- No auto-detect feature in this edition.
